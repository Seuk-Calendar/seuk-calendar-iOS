# Git Branch Creation

브랜치 컨벤션에 맞는 Git 브랜치를 자동으로 생성하는 스킬입니다.

## 트리거 조건

다음 상황에서 이 스킬을 **자동으로** 실행:

1. 사용자가 명시적으로 브랜치 생성 요청 ("브랜치 만들어줘", "새 브랜치 생성해줘")
2. 사용자가 새로운 작업을 시작하려고 할 때

## 실행 단계

### 1. 현재 브랜치 상태 확인

작업 전 Git 상태 확인:

```bash
git status
```

**IF** 변경사항이 있음:
→ 사용자에게 경고 후 진행 여부 확인

**IF** 이미 작업 브랜치에 있음:
→ 새 브랜치 생성 필요성 재확인

### 2. 브랜치 타입 선택

**사용자에게 질문** (AskUserQuestion 도구 사용):
```
어떤 타입의 브랜치를 생성할까요?

1. feat - 새로운 기능 추가
2. fix - 버그 수정
3. env - 환경 설정, 빌드, CI/CD 관련 변경
4. chore - 코드 변경 없는 잡무
5. refactor - 기능 변경 없는 코드 리팩토링
6. docs - 문서 추가 및 수정
7. test - 테스트 추가 및 수정
8. style - 코드 스타일 변경

선택:
```

**추가 타입** (특수한 경우):
- hotfix - 긴급한 프로덕션 버그 수정
- release - 릴리즈 준비 브랜치

### 3. 이슈 번호 확인

**사용자에게 질문**:
```
관련된 GitHub 이슈 번호가 있나요?
(예: 312, 없으면 skip)
```

**IF** 이슈 번호가 없음:
→ 사용자에게 이슈 생성 권장 (create-issue 스킬 참조)

**IF** 이슈 번호 제공됨:
→ 형식 검증 (숫자만 허용)

**선택사항**: GitHub CLI로 이슈 존재 여부 확인
```bash
gh issue view {이슈번호}
```

### 4. 간단한 설명 입력

**사용자에게 질문**:
```
브랜치명에 사용할 간단한 설명을 입력하세요.
(영어 소문자, 2-4 단어, 동사로 시작)

예시: add-commit-rules, implement-home-feed, fix-login-crash

입력:
```

**검증 규칙**:
- 영어 소문자만 허용
- 단어는 하이픈(-)으로 구분
- 2-4 단어 권장
- 동사로 시작 권장

**IF** 형식이 맞지 않음:
→ 재입력 요청

### 5. 브랜치명 생성

브랜치 컨벤션 형식에 따라 브랜치명 조합:

```
{타입}/#{이슈번호}-{설명}
```

**예시**:
- `feat/#312-add-commit-rules`
- `fix/#100-fix-login-crash`
- `docs/#150-update-architecture-guide`

### 6. 브랜치 생성 확인

**사용자에게 확인**:
```
다음 브랜치를 생성할까요?

브랜치명: {생성될_브랜치명}
기준 브랜치: {현재_브랜치}

생성하시겠습니까? (yes/no)
```

**IF** 사용자가 거부:
→ 브랜치 생성 중단

**IF** 사용자가 동의:
→ 다음 단계 진행

### 7. 브랜치 생성

Git 명령으로 브랜치 생성 및 체크아웃:

```bash
git checkout -b "{브랜치명}"
```

**IF** 생성 실패:
→ 오류 메시지 확인 후 사용자에게 보고

### 8. 생성 완료 보고

**사용자에게 보고**:
```
✅ 브랜치가 생성되었습니다!

📋 브랜치 정보:
- 브랜치명: {브랜치명}
- 타입: {타입}
- 이슈 번호: #{이슈번호}
- 설명: {설명}
- 기준 브랜치: {이전_브랜치}

다음 단계:
1. 작업 진행
2. 커밋 (컨벤션에 맞게)
3. PR 생성 (develop 브랜치로)
```

## 엣지 케이스

### Case: 동일한 브랜치명이 이미 존재
→ 사용자에게 알리고 다른 이름 제안 또는 기존 브랜치 체크아웃 제안

### Case: Git 저장소가 아닌 경우
→ `git init` 필요성 안내

### Case: 변경사항이 커밋되지 않은 경우
→ `git stash` 권장 또는 커밋 후 진행 안내

### Case: 원격 저장소에 동일 브랜치 존재
→ 로컬/원격 브랜치 충돌 해결 방법 안내

### Case: 메인 브랜치가 main/develop이 아닌 경우
→ 사용자에게 기준 브랜치 확인

### Case: release 브랜치 생성 시
→ 형식이 다름: `release/<버전>` (예: `release/1.0.0`)

### Case: hotfix 브랜치 생성 시
→ main/master 브랜치를 기준으로 생성해야 함을 안내

### Case: 이슈 번호가 매우 큰 수인 경우
→ 검증 후 사용자에게 재확인
