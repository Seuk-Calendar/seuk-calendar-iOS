# Issue To PR Workflow

GitHub 이슈를 기준으로 작업 시작부터 PR 생성까지 일관된 순서로 처리합니다.

## 입력

- 권장: 이슈 번호 (`<number>`)
- 대체: 작업 내용 요약(이슈 번호가 없는 경우)

## 실행 단계

### 1. 사전 점검 수행

1. `check-memory` 스킬을 먼저 실행해 재발 방지 체크리스트를 적용합니다.
2. `check-rules` 스킬을 실행해 커밋/PR/리뷰 규칙을 현재 요청 기준으로 요약합니다.
3. 작업 트리가 더럽거나(미커밋 변경 존재) 현재 브랜치 상태가 위험하면 먼저 사용자에게 진행 가능 여부를 확인합니다.

### 2. 이슈 번호 확보 (없으면 생성)

먼저 진행 기준이 될 이슈 번호를 확정합니다.

1. 사용자 요청에서 이슈 번호를 추출합니다.
2. **IF** 이슈 번호가 제공된 경우:
   - `gh issue view <number> --json number,title,url`로 존재 여부를 확인합니다.
3. **IF** 이슈 번호가 없거나 누락된 경우:
   - 사용자에게 이슈 번호 또는 작업 내용을 요청합니다.
   - 질문 예시:

```text
이슈 번호를 알려주세요.
이슈가 없다면 작업 내용을 1~3줄로 작성해주세요.
```

4. **IF** 사용자가 작업 내용만 제공한 경우:
   - 사용자에게 이슈 생성 여부를 반드시 확인합니다.
   - 확인 문구 예시:

```text
해당 작업을 이슈로 생성할까요?

작업 내용:
{사용자가 입력한 작업 요약}
```

   - 사용자가 동의하면 `create-issue` 스킬을 호출해 이슈를 생성하고, 생성된 번호를 이번 workflow의 기준 이슈 번호로 사용합니다.
   - 사용자가 거부하면 workflow를 중단합니다.

### 3. 이슈 내용 수집 및 작업 범위 확정

아래 명령으로 이슈 본문과 코멘트를 읽고 요구사항을 확정합니다.

```bash
gh issue view <number> --json number,title,body,labels,assignees,url
gh issue view <number> --comments
```

1. 이슈에서 구현 요구사항, 제외 범위, 완료 조건을 추출합니다.
2. 불명확한 요구사항이 있으면 구현 전에 사용자에게 짧게 확인합니다.

### 4. 브랜치 준비

이슈 번호를 포함한 브랜치를 준비합니다.

1. 브랜치가 없으면 먼저 `create-branch` 스킬을 사용해 브랜치를 생성합니다.
2. `create-branch` 실행 시 브랜치 컨벤션(`<타입>/#<이슈번호>-<설명>`)을 그대로 적용합니다.
3. 타입이 애매하면 `feat`를 기본으로 사용하고, 버그 수정이 명확하면 `fix`를 사용합니다.
4. `create-branch`를 사용할 수 없는 예외 상황에서만 직접 `git checkout -b`로 대체합니다.

### 5. 구현 및 문서 동기화

1. 이슈 본문 기준으로 코드를 수정합니다.
2. 아키텍처/모듈 구조/의존성이 바뀌면 다음 문서를 함께 업데이트합니다.
   - `.agents/rules/Architecture.md`
   - 해당 모듈의 `Module.md`

### 6. 품질 검증

1. 변경된 Swift 파일은 `format-swift` 스킬 또는 프로젝트 포맷터로 정리합니다.
2. 가능한 범위에서 빌드/테스트/린트를 실행합니다.
3. 실행 불가한 검증이 있으면 이유를 결과 보고에 남깁니다.

### 7. 커밋

커밋 컨벤션을 반드시 지켜 커밋합니다.

```text
#<이슈번호> <타입> :: <제목>
```

1. 의미 단위로 커밋을 분리합니다.
2. 제목/본문은 기본적으로 한국어로 작성합니다.

### 8. PR 생성

리뷰 시작 전에 `create-pr` 스킬로 PR을 먼저 생성합니다.

1. PR 제목은 PR 컨벤션 형식(`(#<이슈번호>) <제목>`)을 따릅니다.
2. 본문은 `.github/PULL_REQUEST_TEMPLATE.md` 구조를 유지합니다.
3. 원격 브랜치 미푸시 상태면 먼저 `git push -u origin <branch>`를 수행합니다.

### 9. PR 기준 코드 리뷰 수행 (review-pr 스킬 사용)

1. 반드시 `review-pr` 스킬을 호출해 **이미 열려있는 PR**을 대상으로 리뷰합니다.
2. workflow 문맥에서 호출하므로 `review-pr`의 코멘트 등록 단계는 자동 수행됩니다.
3. 이 단계의 산출물은 다음을 포함해야 합니다.
   - Finding 목록(`P0`~`P3`, 파일/라인)
   - 등록된 PR 코멘트 id/url

### 10. 코드 수정 및 코멘트 응답

1. `review-pr`에서 나온 Finding 중 `P0`, `P1`은 반드시 수정합니다.
2. `P2`는 가능한 범위에서 수정하고, 보류 시 근거를 남깁니다.
3. 수정 후 필요한 검증(테스트/린트/빌드)을 재실행합니다.
4. 수정 커밋을 푸시한 뒤, 9단계에서 생성된 리뷰 코멘트에 답글로 해결 내용을 남깁니다.
5. 각 답글에는 최소한 다음을 포함합니다.
   - 무엇을 어떻게 수정했는지
   - 반영 커밋 SHA
   - 테스트/검증 결과 요약

예시(리뷰 코멘트 답글):

```bash
gh api repos/<owner>/<repo>/pulls/comments/<comment-id>/replies \
  -f body='수정 완료: 알림 권한 부재를 denied로 처리하던 분기를 제거했습니다. (commit: 30f212c, 테스트 통과)'
```

### 11. 잘못된 패턴 memory 기록

반복 가능성이 있는 실수, 사용자 교정 요청, 컨벤션 누락이 있으면 `write-memory` 스킬을 실행합니다.

1. `memory-template` 형식으로 신규 메모리를 작성합니다.
2. `MEMORY_INDEX.md`에 인덱스를 추가합니다.
3. 어떤 예방 규칙을 추가했는지 결과에 명시합니다.

### 12. 이슈 완료 코멘트 등록

작업/리뷰 반영이 끝나면 대상 이슈에 완료 코멘트를 반드시 등록합니다.

1. 이슈 코멘트에는 최소한 다음을 포함합니다.
   - 변경 요약(무엇을 반영했는지)
   - 남은 TODO(후속 구현/결정 필요 항목)
   - 관련 PR 번호/URL
2. 백틱(`\``), `+N` 같은 문구가 포함될 수 있으므로 `--body-file` 방식으로 코멘트를 등록합니다.
3. 등록 후 코멘트 URL을 결과 보고에 포함합니다.

예시(권장):

```bash
cat > /tmp/issue-<number>-comment.md <<'EOF'
## 변경 요약
- ...

## 남은 TODO
- ...

관련 PR: <url>
EOF

gh issue comment <number> --body-file /tmp/issue-<number>-comment.md
```

## 결과 보고 형식

작업 종료 시 아래 항목을 순서대로 보고합니다.

1. 대상 이슈: 번호, 제목, URL
2. 브랜치명
3. 커밋 목록
4. PR 번호와 URL
5. 리뷰 Finding 목록 및 PR 코멘트 URL
6. Finding 반영 결과(수정 커밋 SHA + 코멘트 응답 URL)
7. memory 기록 여부(기록 파일명)
8. 이슈 완료 코멘트 URL

## 예외 처리

- 이슈 번호가 없고 작업 내용도 제공되지 않으면, 필요한 정보가 확보될 때까지 workflow를 시작하지 않습니다.
- 제공된 이슈 번호가 존재하지 않으면 신규 이슈 생성 여부를 먼저 확인합니다.
- 사용자가 이슈 생성 확인에서 거부하면 workflow를 중단합니다.
- `gh auth` 또는 저장소 권한 문제가 있으면 인증/권한 상태를 먼저 해결합니다.
- 외부 변경(내가 만들지 않은 예상치 못한 변경)이 발견되면 작업을 멈추고 사용자 지시를 받습니다.
